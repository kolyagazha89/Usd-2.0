# USD — безопасная приёмка релиза на Ubuntu

Цель: выпустить обновление только на `app.usd-russia.ru`. **Не менять** `usd-russia.ru`, не очищать PostgreSQL и не запускать исторический импорт повторно.

## Особый переход: версия безопасности `e0c244b` → команды USD

На `app.usd-russia.ru` и `api.usd-russia.ru` ранее подтверждена ревизия `e0c244bad7f77f576f1889abe36bf1dc0a9db735`. В `main` добавлена миграция `20261030060000_team_commanders`.

Однократный установщик теперь различает **совпадающую схему** (перестановка/восстановление runner не должна блокироваться старым первичным upgrade helper) и **строго проверенную добавочную миграцию**. Допускается только точный Prisma tree `a22c242dd0c6dfa9554f179cf705b39499a68967` и blob SQL `8a4a598f9b52a46d59d3e2e4934a30136fbcf753`, при исходной API-ревизии `e0c244b...` и единственной ожидающей миграции таблиц команд. Другие миграции или изменённые SQL остаются заблокированы. Выпуск выполняется оператором на Ubuntu, а не GitHub Actions или чатом.

**До запуска установщика** необходимо проверить физический источник и независимость бэкапов, свободную память/диск и состояние Docker. Для допуска данной миграции установщик обязан провести свежий dump PostgreSQL, проверенную копию на другом накопителе, полное восстановление и Prisma migrate в отдельной PostgreSQL 18, а уже затем применить разрешённую миграцию с проверкой контейнера БД и количества строк. Не обходить остановку и не применять миграцию вручную через `prisma migrate deploy` без этих проверок.

Подготовка/контроль **без применения миграций**:

```bash
cd /home/usd/usd-deploy
git fetch origin main
git switch main
git pull --ff-only origin main
sudo python3 deploy/home-pc/release-readiness.py --live
```

После успешного анализа и доступных подписанных образов контролируемый установщик:

```bash
cd /home/usd/usd-deploy && sudo bash deploy/home-pc/setup-home-pc.sh
```

Установщик не может автоматически включить GitHub-trigger, пока переменная GitHub Actions `USD_HOME_PC_HOST_APPROVED` не установлена в `true`. После успешного первого релиза он проверяет эту переменную и, если она отсутствует, просит в SSH **явно** ввести `ENABLE-USD-PRERELEASE` для разрешения только предрелизного автодеплоя с неизменной проверенной схемой. Затем устанавливает GitHub Actions variable и проверяет её повторно, прежде чем запускать контрольный второй релиз. Без терминала или подтверждения прекращает настройку, сохраняя работающий сайт; самостоятельное создание контрольного коммита не происходит. Локальный HDD всё ещё не заменяет отдельное off-host хранилище.

Он не сбрасывает базу и не меняет `usd-russia.ru`. Он должен **остановиться с ошибкой**, если схема отличается от разрешённой или нет проверенного backup/restore; не подменять такую ошибку записью файла approvals. Подтверждение второго SHA-пуша и совпадения публичных ревизий остаётся обязательным условием готовности. Локальный второй HDD **не является off-host копией**: по мастер-плану независимый бэкап на другом устройстве/провайдере ещё необходим для окончательной эксплуатационной готовности.

## 1. Проверка без изменений

После слияния и публикации образов на самом Ubuntu-хосте:

```bash
cd /home/usd/usd-deploy
git fetch origin main
git checkout main
git pull --ff-only origin main
sudo python3 deploy/home-pc/release-readiness.py --live
sudo python3 deploy/home-pc/release-readiness.py --live --json
```

Результат `NOT READY` означает **стоп**, а не разрешение автоматически отключать защитные политики. Отчёт не раскрывает содержимое `.env` и конфигураций резервного копирования. Он проверяет только наличие и структуру предусловий, **не заменяет** реальную проверку восстановления БД и медиа.

## 2. Проверка GitHub

Перед релизом зафиксировать конкретный полный SHA `main` и убедиться, что для него завершились успешно: Backend CI, Frontend CI (если менялся фронтенд), Home PC deployment safety checks, Competition journey и Public browser QA. Проверить, что опубликованы оба OCI-образа `api` и `frontend` с совпадающей меткой `org.opencontainers.image.revision`.

## 3. Резервное копирование и миграции

Не запускать автоматический релиз, если нет проверенной **независимой** копии PostgreSQL и S3/медиа, доступной вне хоста, и успешного восстановления на временное хранилище. Если дерево `backend/prisma` отличается от одобренного, автоматический деплой должен остановиться: миграции допускаются только после отдельной репетиции на восстановленном дампе и явного одобрения оператора.

## 4. Выпуск

Только после всех проверок и подтверждения доступности хоста — использовать уже предусмотренный `usd-auto-deploy.service` с одобренными политиками. Не переписывать `.env` вручную и не подменять SHA тегом `latest`. Если политика запрещает выпуск, устранять причину и повторять проверки, а не обходить её.

## 5. Приёмка

Проверить `https://app.usd-russia.ru/usd-release.json` и `https://api.usd-russia.ru/release`: обе ревизии должны совпадать с целевым SHA. Проверить вход и выход, смену пароля, личный кабинет участника, конфигурацию автомобиля, регистрацию на этап, инспекцию, ввод результатов, записи и права администратора/судьи, мобильные экраны 320/390 px, изображения и загрузку медиа. Убедиться, что основная публичная площадка `usd-russia.ru` не менялась.

## 6. Стоп/откат

При несовпадении ревизий, ошибках API, падении smoke-тестов, проблемах с БД или недоступности критических функций **остановить продвижение**. Использовать существующий механизм отката контейнеров только после проверки совместимости схемы. Не восстанавливать дамп поверх живой БД без отдельного решения оператора.

Это инструкция для оператора, **не свидетельство** выполнения проверки на реальном сервере.
