# Стабилизация платформы — 18 октября 2026

Основа: main 768e25b. Ветка: codex/platform-reliability-and-speed. Этот документ описывает подготовленный код, не production-выпуск.

## Реализовано

- Исторический поиск не выдаёт госномера и контактные поля; закрытый профиль доступен для обнаружения только владельцу legacy email. Ответ формируется явно.
- Публичное чтение, credential attempts, refresh/logout и рабочие записи используют отдельные квоты. После проверки JWT добавлены отдельные квоты пользователя. OPTIONS не расходует квоту; повторные попытки входа дополнительно ограничены по IP + hash email. Несколько API-реплик требуют отдельного общего limiter.
- Создание/исправление результата, аудит, рекорд и места выполняются в одной Serializable-транзакции. Сбой откатывает всё. Одинаковый повтор от того же автора возвращает уже сохранённый результат; другой результат остаётся конфликтом. Serialization failures повторяются ограниченно, без внешних эффектов внутри транзакции.
- Миграция добавляет DB-trigger и индекс нормализованного госномера. Защищает все пути записи, включая импорт и конкурентные запросы. Старые данные не удаляются и не сливаются. Если исторические дубли уже есть, они остаются для отдельного разбора; новые конфликты запрещены.
- Сотрудник с custom role может управлять своим аккаунтом. Управление чужими пользователями/ролями остаётся ADMIN-only. Добавлено разрешение componentCatalogRequests и исправлен просмотр site-assets сотрудниками с правами media.
- Разделы админки/конфигурации загружаются по требованию, включая тяжёлый импорт. Добавлены Suspense, browser acceptance tests и бюджет статического публичного JS.
- Исправлены буквальные обратные слэши+n в CSS. SheetJS 0.18.5 заменён официальной поставкой 0.20.3; сохранён frontend lock-файл; CI и Docker используют npm ci. Postinstall-сборка убрана.
- SEO-настройки CMS подключены к title, description, canonical и OG; этапы получают собственные метаданные и SportsEvent JSON-LD. Это клиентские метаданные: server-rendered social previews/SSG пока не реализованы.
- Production bootstrap вынесен в createApplication; API-тесты используют те же глобальные guards, middleware и ValidationPipe.
- Для нового same-origin развёртывания поддержан /api, cookie-only refresh без токена в JSON/localStorage, настраиваемый cookie path и SameSite=lax. Старый cross-site fallback сохранён для совместимости. Небезопасные запросы с недоверенным Origin отклоняются.
- Подготовлена конфигурация домашнего Windows-сервера: приватная PostgreSQL, лимиты памяти, журналы, named tunnel, один HTTPS-origin, ежедневный pg_dump. Compose проверен синтаксически; это не развёрнутый production.

## Проверки

Проверены обе production-сборки; 257 unit-тестов плюс 2 отдельных теста cookie-сессий; 8 API-тестов; 6 браузерных тестов; dependency audit (0 production-находок frontend); backend lint и compose config. Новая миграция применена только к одноразовой PostgreSQL localhost:55432/usd_audit. В тестах есть rollback при искусственном сбое пересчёта, повтор сохранения, конкурентные госномера, скрытые профили, права судьи и блокировка недоверенного Origin. Браузерные проверки используют desktop/mobile размеры Chromium; это не проверка настоящей камеры iPhone.

При промежуточной сборке стартовый JS уменьшился с 1 414,22 kB / gzip 412,46 kB до 561,62 kB / gzip 157,89 kB. После добавления SEO итог: 563,84 kB / gzip 158,95 kB (примерно на 61,5% меньше gzip исходного стартового файла). Публичный статический граф — 563 839 байт, проверяемый бюджет — 650 000 байт. CSS остаётся большим и требует дальнейшего упорядочивания. Тест NAT проверяет логику limiter, а не предельную пропускную способность железа.

## Порядок выпуска и границы

1. Проверить PR и зелёные CI.
2. Создать backup и проверить восстановление копии действующей базы; проверить новую миграцию на ней, особенно исторические номера/дубли и время создания индекса.
3. Заполнить конфигурацию сервера, перенос БД/медиа/почты и подтвердить план запуска.
4. После отдельного подтверждения выполнить production-миграцию/публикацию, сверить коммит и пройти приёмку. Действующий корневой домен не переключать автоматически.

Ни production-данные, ни DNS этим изменением не меняются. Полноценная автономная площадка, QR credentials с отзывом, очередь/вызов участника, серверные OG/SEO, исчерпывающая мобильная приёмка и нагрузочные испытания остаются следующими этапами. Статус «лучший среди конкурентов» не подтверждается одним техническим релизом.

## Согласованный следующий этап: локальный ноутбук

Домашний Windows-ПК — основной сервер. На площадке — отдельный ноутбук с локальным Wi-Fi. Сначала реализовать и проверить:

1. Экспорт подписанного пакета выбранного этапа с минимальными данными, версией и сроком действия, без production-токенов и посторонних аккаунтов.
2. Локальные учётные записи/полномочия судей, HTTPS/камера на настоящих телефонах, резервный ручной поиск.
3. Надёжный журнал операций и стабильные ID запросов; серверные квитанции, повторная отправка и восстановление после перезапуска.
4. Явные конфликты для инспекций, классов, результатов и отмен; решения организатора с аудитом. Никакой тихой перезаписи по времени телефона.
5. Приёмка: 30 минут без внешней сети, несколько судей, перезапуск ноутбука, конфликтующие правки, возвращение сети и сверка центральных данных.

VPN/прокси может помочь маршрутизации, но не является основой работоспособности при отсутствии мобильного канала.
