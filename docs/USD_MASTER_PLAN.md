### Автоматический деплой

**Цель — как на Railway: отправили изменения в GitHub, и сайт обновился самостоятельно.**

Необходимый процесс:

1. Разработчик отправляет изменения в GitHub.
2. Запускаются проверки CI.
3. GitHub Actions собирает Docker-образы API и frontend.
4. Образы публикуются в GHCR с неизменяемыми SHA-тегами.
5. Ubuntu получает сигнал на обновление через защищённый GitHub Runner.
6. Сервер проверяет результаты CI и соответствие версий.
7. Создаются и проверяются резервные копии.
8. Проверяется совместимость схемы Prisma.
9. Новые контейнеры запускаются без пересоздания базы данных.
10. Проверяются API, frontend и доступность публичного сайта.
11. При ошибке выполняется безопасный откат.
12. Успешное обновление фиксируется в журнале.

Обычные обновления, не требующие отдельного согласования миграций, должны проходить автоматически.

## 9. Регистрация и проведение соревнований

### Регистрация

- Онлайн-регистрация участником.
- Регистрация на месте судьёй или администратором.
- Поиск существующего профиля.
- Создание нового участника **сразу на въезде**, даже если у него ещё нет аккаунта, профиля и конфигурации: минимум ФИО, марка/модель и валидный госномер, с проверкой исторических дублей и согласий.
- Выбор существующего автомобиля либо создание автомобиля без необходимости заполнять компоненты аудиосистемы на стойке.
- Для регистрации на месте разрешён явный черновик конфигурации с флагом «не заполнена»; нельзя выдавать этот черновик за проверенную конфигурацию и нельзя автоматически распространять исключение на онлайн-регистрацию. Черновик должен быть дополняемым через ЛК/операторский сценарий с сохранением достоверных исторических снимков.
- Участник с уже существующим профилем (включая исторический) может добавить **новый автомобиль прямо на въезде**, без создания нового профиля; дубли госномеров проверяются с учётом транслитерации, а сохранение подтверждается в журнале.
- **Результаты в день этапа можно вносить без конфигурации.** Это обязательно для полевых условий: оборудование и интернет могут быть недоступны, но судейство и номер участника не должны зависеть от ввода аудиосистемы.
- **Обязательное заполнение после этапа:** участник или оператор сохраняет фактическую версию оборудования и подтверждает её в регистрации, в том числе после внесения результатов или завершения этапа. Сохранять **неизменный оригинальный снимок дня этапа** и добавлять датированное поле документального дополнения с автором и версией; не переписывать результат, судью, номера или старую конфигурацию.
- **Блокировать новую регистрацию на следующий этап**, если существует активное участие в уже прошедшем этапе с незаполненной конфигурацией. Текущее участие и дополнительные регистрации на том же этапе не блокировать, отменённые заявки не учитывать. Проверка обязательна в backend и для участника, и для судьи / ADMIN (без скрытого обхода).
- **Push после этапа** через согласованный канал напоминаний: на 1-й, 7-й и 14-й календарный день после этапа, без дублей, только участникам с активной подтверждённой привязкой аккаунта и добровольной подпиской. Перед фактической доставкой повторно проверять, не заполнена ли конфигурация. Для профиля без привязанного аккаунта push недоступен: показывать задачу оператору и при последующем связывании профиля.
- **Настоящая автономная работа судей без доступа к API** (локальная очередь ввода/синхронизация/разрешение конфликтов) — отдельная задача offline-first. Разрешение пустой конфигурации само по себе не гарантирует доступность сайта и сервера без интернета, не объявлять offline-ready до испытаний в режиме полного отключения сети.
- **ОСНОВНАЯ офлайн-архитектура по согласованному сценарию:** на площадке один ноутбук с локальными USD API + PostgreSQL + S3/RustFS + frontend; обычный Wi-Fi-роутер объединяет телефоны судей и администратора **без интернет-канала**. Все судьи видят одни и те же данные через единый локальный сервер, не через независимые браузерные копии.
- Подготовка за пределами площадки: отдельный набор локальных секретов/томов, зафиксированные образы, версия Prisma, безопасный экспорт только нужного этапа и связанных участников/автомобилей/классов, аудиторская подпись экспорта, актуальность правил и полномочий, восстановление медиа. Никакого автоматического копирования всей боевой БД с Ubuntu на ноутбук.
- **Реализован этап подготовки (без импорта):** ADMIN вручную скачивает подписанный Ed25519 пакет этапа; backend ограничивает экспорт одним этапом и минимальным составом персональных данных, пишет аудит и требует специально настроенный секрет на Ubuntu. На ноутбуке отдельная CLI проверка подписи, срока, связей и отсутствия лишних полей. Только следующий блок может добавлять безопасное развёртывание этого пакета в изолированную локальную БД и полноценную синхронизацию; до этого реальная площадка не готова.
- Через роутер — статический IP ноутбука/DHCP reservation, HTTPS с проверенным и доверенным на телефонах локальным сертификатом, 443 только на LAN-интерфейсе; PostgreSQL и RustFS недоступны по Wi-Fi напрямую. Работоспособность не зависит от DNS, публичного домена или внешних туннелей.
- Судейские действия на площадке (создание профиля, регистрация, инспекция, изменение класса, судейство) записываются в локальную БД и неизменяемый журнал операций с уникальными ID. После возвращения интернета центральный API принимает операции поштучно, проверяет RBAC и ограничения и подтверждает/отклоняет с ручным разрешением конфликтов. Не допускается молчаливое затирание результатов и исторических снимков.
- IndexedDB/зашифрованный пакет с локальным QR-поиском — **резервный режим одного устройства**, а не основной сценарий двух и более судей. До реализации сетевого хаба, подготовки данных и безопасной синхронизации не объявлять полноценную офлайн-готовность.
- **Критерий приёмки:** отключить WAN физически, открыть USD на двух реальных телефонах через роутер и ноутбук, одновременно зарегистрировать/осмотреть/судить, увидеть изменения другого судьи без обновления из интернета; перезапустить ноутбук и проверить сохранность; восстановить WAN, синхронизировать с центральным Ubuntu, разобрать конфликты и получить ноль необработанных операций, сохранив центральные исходные данные. Проверить блокировку внешнего API и отсутствие публично открытой БД/медиа.

- После выдачи номера сразу открывать инспекцию новой регистрации, не требовать повторного поиска; участник с отсутствующей полной конфигурацией должен быть явно виден судьям.
- Выбор автомобиля и конфигурации.
- Выбор классов.

- Корректное назначение номеров.

Сохранить действующие направления и классы SPL, BFSPL, BassRace и Storm Wall.

## 10. Роли, команды и права

Базовые роли:

- ADMIN.
- PARTICIPANT.

Дополнительные судейские и операционные полномочия — через гибкую RBAC-модель.

Требования:

- Редактор ролей.
- Настройка прав по модулям и действиям.
- Проверка доступа на сервере.
- Корректная работа личного кабинета у судей.
- Переход из публичной части в админку и обратно.
- Команды — существующие независимые объединения автозвукового сообщества (например, Team Deaf Bonce, Team Avatar, Team Aura), а не подразделения USD.
- Только администратор USD создаёт карточку команды на сайте и назначает командира.
- Участник подаёт заявку на вступление; командир принимает или отклоняет её и управляет составом своей команды.
- Командир не получает административных или судейских прав USD по факту назначения.
- Публичная страница команды, её состав, новости и достижения.
- **Промежуточный достоверный шаг:** выводить по этапам опубликованные результаты текущего одобренного состава команды, только для участников с публичным профилем. Обязательно подписывать этот блок «Выступления текущего состава» и не выдавать его за исторические победы команды.
- **Для настоящих командных достижений и зачётов** сохранять неизменную принадлежность участника к команде на дату конкретного этапа, результаты, баллы и порядок фиксации смены команды. Без этого запрещено автоматически приписывать прошлые выступления новой команде. До внедрения соответствующих снимков официальные командные медали и очки не рассчитывать.
- **Снимок на первой пройденной инспекции (новый PR):** для каждой регистрации при первом PASSED сохранить ID и историческое название команды либо явное отсутствие членства. После смены команды/названия эта информация неизменна. Этапы с уже существующими историческими инспекциями и импортированными результатами не приписывать задним числом.
- Отдельный публичный раздел показывает *личные выступления за команду, подтверждённую при инспекции*. Вывод только для публичных профилей, активных регистраций и опубликованных результатов этапов. Лимит 500 обозначать явно. Старый раздел «Выступления текущего состава» сохраняется и не считается командными медалями.
- **Командный зачёт по очкам ещё не реализован**: для него нужно согласовать правила начисления очков, несколько машин одного участника, изменения результатов и фиксацию результата по времени.
- **Фотоновости и достижения команд (PR #368, до слияния не считать готовыми на сервере):** до восьми JPG/PNG/WebP на одну новость, хранение в локальном RustFS через авторизованный API, доступ к черновикам только командиру/ADMIN, запрет публичного просмотра до утверждения и отдельный акт одобрения публикации администратором. Сервер проверяет идентификаторы и завершённую загрузку каждой фотографии; фотографии нельзя присоединять к чужому посту. Nullable миграция для gallery references должна пройти безопасный выпуск.
- **Осталось по медиаконтенту:** согласие на публикацию фотографий людей/автомобилей, удаление неиспользуемых загруженных файлов, уведомления о модерации и проверка на реальном RustFS/Ubuntu.
- **Дальнейшее развитие (отдельный этап, не считать реализованным):** командные рейтинги, статистика выступлений команд и командные зачёты на соревнованиях USD. До реализации согласовать правила начисления очков, учёта смены команды и отображения исторических результатов.

### Самостоятельная подсистема команд USD — обязательная часть конечного продукта

Команда — полноценное объединение автозвукового сообщества со своим публичным разделом и рабочим кабинетом, а не просто строка `team` в профиле участника. **Наличие API/таблиц и базовой страницы команды ещё не означает готовность этой системы.** Функциональность развивается внутри единого аккаунта и дизайна USD, без отдельной авторизации и без выдачи командирам прав организатора.

**Роли и полный жизненный цикл состава:**

1. Только ADMIN создаёт / архивирует команду, назначает и меняет командира, разрешает споры и может исправить состав с обязательным журналом действий.
2. Командир управляет описанием, обложкой, логотипом и другими разрешёнными данными своей команды, обрабатывает заявки на вступление, приглашает участников, удаляет участников и передаёт запросы администратору. Действия ограничены **своей** командой и проверяются на backend.
3. Участник видит свою команду и историю членства, подаёт / отменяет заявку, принимает приглашение, может выйти из команды. Дубли заявок, обход лимита одной активной команды, гонки одновременных решений и повторные запросы должны безопасно обрабатываться сервером.
4. Командир может быть обычным участником соревнований, а ADMIN и судьи могут состоять в команде. Назначение командиром **не** добавляет административных или судейских полномочий.
5. Изменение состава или командира не уничтожает прошлые командные результаты. Хранить историю вступления/выхода и датированную принадлежность на момент этапа; исторический зачёт не должен пересчитываться задним числом по текущему составу.

**Собственный публичный раздел команды:**

- Обложка, логотип, название, город/регион, описание и ссылки (проверка допустимых URL), публичный список состава и командир; удобная адаптивная мобильная версия Dark Velocity.
- Лента **новостей команды с фотографиями**: отдельные публикации с заголовком, текстом, датой, обложкой, галереей изображений и безопасным предпросмотром. Создание, редактирование, публикация/снятие с публикации и удаление — через кабинет командира в пределах его команды; ADMIN может модерировать.
- Изображения загружаются в локальное S3/RustFS с проверкой типа, размера и доступа. Удаление новости не должно удалять медиа, используемые в других публикациях, а отсутствие снимка даёт фирменную заглушку USD. Для медиа и текстов — модерация и защита от XSS/опасных ссылок.
- **Достижения команды по каждому этапу**: сезон, этап и город, участники и автомобили на момент участия, направления/классы, места, измерения и рекорды, переходы к исходным протоколам и профилям. Сводные карточки побед/подиумов/рекордов и история всех сезонов.
- Достижения рассчитываются только по утверждённым результатам USD (без ручной подмены командиром), корректно учитывают смену команды, отмену или исправление результата, историческую принадлежность и архивные этапы. Исключения отдельных направлений из рекордов сохраняются.
- Отдельные внутренняя панель командира и публичная страница команды: список заявок/приглашений, состав, редактор профиля, редактор новостей и галерей, статистика выступлений, журнал разрешённых действий. Не прятать основные функции в многочисленные модалки.

**Командный зачёт как отдельный функциональный блок:** до внедрения согласовать правила очков, количество зачётных участников, ограничения по направлениям, тай-брейки, переходы между командами, публикацию итогов и пересчёт после исправлений судьями. Затем реализовать рейтинг команд по этапу/сезону и историческую статистику с детальными объяснимыми расчётами.

**Приёмка подсистемы:** browser/API/E2E сценарии ADMIN → назначение командира → заявка/приглашение → приём/выход → новость с несколькими фото → публикация → результаты этапа → командные достижения → смена состава. Проверить попытки управления чужой командой, приватные данные, конкурирующие заявки, неподтверждённые аккаунты, мобильный интерфейс и сохранность архивных достижений. Обязательны тесты с PostgreSQL 18 и реальным локальным S3. До прохождения этих сценариев не помечать команды завершёнными.

## Дополнение 2026-11-08 — шапки и уведомления ADMIN о привязке

- Верхние шапки публичного сайта и ЛК резервируют фактическую высоту через ResizeObserver, включая safe-area и переносы при увеличенном шрифте. Нижние мобильные панели закреплены в body, с отдельным слоем отрисовки для Safari; viewport-fit=cover сохраняет масштабирование жестами.
