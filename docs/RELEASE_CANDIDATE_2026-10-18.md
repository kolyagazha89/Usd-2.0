# ЮСД — релизный кандидат (18 октября 2026)

**Статус: кандидат для приёмки, а не разрешение на production-деплой.** Публичное название проекта — ЮСД. Сборка не меняет домен, Railway, Cloudflare, базу или файлы пользователей.

## Что производит GitHub Actions

Workflow `.github/workflows/release-candidate.yml` при PR к `main` или ручном запуске:

1. Скачивает **точный SHA исходной ветки** (а не плавающую ветку/непредсказуемый merge-commit).
2. На фиксированных npm lock-файлах компилирует NestJS/Prisma и React (`VITE_API_URL=/api`, `VITE_AUTH_SESSION_MODE=cookie`); проверяет лимит JS.
3. Проверяет конфигурацию Windows-home Docker Compose и **собирает** API и frontend Docker-образы (не запускает базу и сервисы).
4. Прикладывает в GitHub Actions артефакт `usd-rc-<sha>` с файлами `usd-release-source.tar.gz` (код + Compose + инструкция), `usd-public-dist.tar.gz` (собранная публичная часть), `RELEASE-MANIFEST.txt` и `SHA256SUMS`.

Сборка **не публикует** Docker-образы в реестр и **не выполняет** миграции производственной БД. GitHub Actions сохраняет пакет 14 дней. Проверка checksum после скачивания: `sha256sum -c SHA256SUMS` (Linux/WSL). Для Docker-развёртывания использовать исходный архив: в нём лежат оба Dockerfile, package-lock, backend, frontend и deploy/windows-home. `dist` — отдельный проверочный frontend-артефакт, не самостоятельный backend-деплой.

## Блокеры выпуска (не отмечать пройденными без доказательств)

- [ ] **Подлинная резервная копия БД и медиа**: сохранена независимо от сервера, тестово восстановлена в изолированную PostgreSQL 16.
- [ ] На **восстановленной копии** применить `prisma migrate deploy`; проверить индексы, дубли госномеров, внешние ключи и времена выполнения. Миграция `20261018150000_guard_car_plate_identity` добавляет DB-trigger и нормализацию. Старые дубли сохраняет; новые конфликты отклоняет. Нужно проверить исторические и технические госномера в реальных данных, не исправлять их автоматически.
- [ ] Пройти read-only preview исторической очистки в тестовой базе; проверить состав затронутых сущностей. Execute только в тестовом окружении и только после отдельной проверки scope/backup, затем повторный импорт по результатам.
- [ ] Backend CI (миграции в одноразовой PostgreSQL, unit/e2e, lint и dependency audit), Frontend CI (Playwright desktop/mobile, build/budget) и Release Candidate workflow — **зелёные на одном SHA**.
- [ ] Приёмка на реальном устройстве: кабинет/почта/сброс пароля, регистрация машины и на этап, QR-камера, общая инспекция, BassRace, исправление класса, результаты/места/рекорды, privacy и кастомные роли.
- [ ] Проверить на целевом компьютере HTTPS и cookie refresh, восстановление после перезапуска, отправку email, сохранение фото, журналы, бэкапы, нагрузку и доступность.
- [ ] Утвердить юридические документы у организатора, заполнить реквизиты, проверить публикацию согласий/политик и уведомление Роскомнадзора.
- [ ] Сверить версию работающего сайта/бэкенда с SHA кандидата; только после приёмки отдельно разрешить переключение домена/DNS.

## Перед переносом на Windows-home

1. В Windows/WSL2 установить Docker Desktop, обеспечить стабильный SSD, автозапуск и резервное питание. В архиве `deploy/windows-home/README.md` — подробная инструкция.
2. Извлечь **usd-release-source.tar.gz** в отдельную директорию, скопировать `deploy/windows-home/.env.example` в `.env`, подставить реальные секреты **локально** (не в репозиторий/чат). Проверить `docker compose --project-directory deploy/windows-home -f deploy/windows-home/docker-compose.yml config --quiet`.
3. Проверить импорт восстановленной БД в изолированный контейнер, миграции и тестовые операции. Не запускайте `api` с production `DATABASE_URL` до одобрения — backend при старте автоматически выполняет миграции.
4. После разрешения запуска: `docker compose --project-directory deploy/windows-home -f deploy/windows-home/docker-compose.yml --profile public up -d`. Named Tunnel требует собственной настройки; порт PostgreSQL наружу не публиковать.
5. Сохранить контрольные суммы и точный SHA релиза в журнале выпуска. Backup-volume на том же диске **не заменяет** независимую копию.

## Что **не** включено в этот релиз

Автономный ноутбук площадки и двусторонняя offline-синхронизация, реальные мобильные нагрузочные испытания, SSG/серверные OG-превью и юридическое утверждение: отдельные этапы и не могут считаться готовыми после прохождения CI. Старый Timeweb deployment остаётся альтернативой, не основанием запускать оба окружения одновременно.
