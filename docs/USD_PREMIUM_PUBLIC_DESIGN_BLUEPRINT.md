# USD Premium · Public Design Blueprint

**Статус:** дизайн-спецификация, не реализованная функциональность.  
**Владелец продукта:** USD (публично только «USD» / «ЮСД»).  
**Цель:** сначала единый премиальный дизайн публичной части, затем реализация в текущем React/Vite и перенос утверждённого конфигуратора.  
**Главная задача:** [#283](https://github.com/kolyagazha89/Usd-2.0/issues/283).

### Типографика и композиция

- Главная desktop: крупный редакционный hero, допускаются заголовки до 96 px с контролем переноса; мобильная: 42–58 px (в зависимости от ширины) без обрезания слов.
- Заголовок раздела desktop 40–48 px, mobile 26–34 px. Карточки 16–20 px. Основной текст 15–16 px.
- На мобильных формах размер `input` / `select` / `textarea` **не меньше 16 px**, чтобы Safari не увеличивал страницу при фокусе.
- Основной контент desktop ограничен `max-width: 1320px`. Отступы desktop 48–64 px, tablet 24–32 px, mobile 16–20 px.
- Радиусы: `12px` элементы управления, `16–22px` карточки, `24px` большие баннеры.
- Применять мягкий визуальный свет только на hero и важных highlights; не использовать красные свечения на каждом элементе.
- Факты и измерения выше декоративности. Все метрики имеют единицы: **dB** для SPL/BFSPL/BDW; **m/s** для Storm Wall.

### Компонентный контракт

- `PublicShell`: компактные общие header/footer; верхняя навигация desktop и мобильный drawer; пропуск к контенту.
- `PublicHero`: CMS-managed заголовок/подзаголовок/фон и 1–2 чётких действия.
- `StageCard`, `ResultCard`, `RecordCard`, `PersonCard`, `TeamCard`, `NewsCard`, `PartnerCard`.
- `DirectionPill`, `ClassChip`, `StatusChip`, `SeasonSwitcher`, `EmptyState`, `LoadingSkeleton`, `ErrorState`.
- `PublicField`, `PublicSelect`, `PublicSearch`, `PublicTextarea`, `PublicUpload`: единая высота/фокус/состояния.
- `PrimaryAction`, `SecondaryAction`, `GhostAction`, `BackLink`, `Breadcrumbs`, `PageHeader`.
- `StageRegistrationStepper`, `ConfigurationReadiness`, `VersionHistory`, `AssetRequestStatus`.
- Семантические `button`/`a` вместо кликабельных `div` где возможно.

## 3. Маршруты: **реальное состояние** vs планы

Проверено по `frontend/src/App.tsx` на 21.10.2026:

**Существующие публичные маршруты:** `/`, `/stages`, `/stages/:id`, `/results`, `/records`, `/rules`, `/privacy`, `/terms`, `/consent`. `/login` и `/participant` обслуживаются отдельными экранами. Настраиваемое публичное меню сейчас допускает только `/`, `/records`, `/stages`, `/rules`.

**Предлагаемые новые разделы** (участники/команды/новости/партнёры/документы) нужно создавать только с реальными маршрутами и backend/CMS data. **Не вставлять ссылки на несуществующие маршруты в рабочий header.** Дизайн может предусматривать эти разделы заранее.

## 4. Состав страниц / desktop + самостоятельная mobile-компоновка

### 4.1 Главная

**Above the fold:** фирменная типографика, настоящий CMS hero, чёткий переход к ближайшему этапу и результатам; визуальная деталь звуковых частот с уважением `prefers-reduced-motion`. На мобильном первый экран не перекрывать высоким хедером.

Последующие блоки обязаны быть связаны с настройками CMS и серверными данными:
1. Ближайший этап: только из реальных опубликованных, статус регистрации и CTA.
2. LIVE-трансляция и LIVE-результаты — только если разрешены конфигурацией.
3. **Шесть последних результатов** по утверждённой логике: **3 SPL, 2 BFSPL, 1 BDW SPL**, не несколько победителей одного класса.
4. Официальные рекорды из опубликованных результатов; не выдумывать данные.
5. Новости, партнёры, информация для начинающих (включаются и сортируются CMS).

### 4.2 Календарь этапов + карточка этапа

- Сезоны **2026 / 2025**, архив, состояния «Регистрация открыта», «Закрыта», «Завершён».
- Карточка: город, дата, адрес если имеется, афиша, доступные направления, статусы и CTA.
- Страница этапа: программа/адрес/карта по существующим данным, классы, регламент, результаты, CTA регистрации. Форма/перерегистрация должна быть частью рабочего процесса, не декоративным макетом.
- Mobile: одноколоночные карточки 16px, табы сезонов с горизонтальным scroll и видимым selected state.

### 4.3 Регистрация

- Страница вместо каскада модальных окон: выбор автомобиля → направления и классы → подтверждение → результат.
- Одна активная регистрация на автомобиль/этап; несколько классов, номера в рамках существующей backend-логики, отдельные BassRace номера.
- Проверка направлений: SUB нужен SPL / BassRace / Storm Wall; FRONT — BFSPL; REAR — BDW SPL.
- Отдельные состояния: нет конфигурации, ещё не подтверждён email, техосмотр, отмена/повторная регистрация, невозможность отправки и уже зарегистрированный автомобиль.
- Сумма: основной класс **2 000 ₽**, дополнительный **2 000 ₽** (только из реальных правил/настроек; UI не должен скрыто хардкодить бизнес-логику). Оплата на месте.
- Mobile: компактный stepper, summary перед отправкой, фиксированное действие с `env(safe-area-inset-bottom)`.

### 4.4 Результаты

- Фильтр этап / сезон / направление / класс; поиск участника, доступность с клавиатуры.
- Карточки mobile вместо нечитабельной desktop-таблицы.
- Чёткие места/значения/дата/этап; автомобиль только если публичен по данным API.
- Пустые данные не подменять результатами другого этапа.
- Единицы **m/s** для Storm Wall, **dB** для остальных направлений.

### 4.5 Рекорды

- Таблицы по направлению, классам и периоду; тип рекорда всегда виден.
- **BassRace исключён из официальных рекордов.** Остальные зависят от флагов публикации конкретных классов. Не менять существующую логику Storm Wall без требований.
- При равных измерениях — раньше полученный результат имеет приоритет.
- Публично не помечать результаты как «исторический» — архивные этапы представлены как обычные завершённые этапы.

### 4.6 Участники, команды

- Дизайн поиска участников/команд, профиля, авто и публичных достижений, история по этапам.
- Скрытые автомобили/контактные данные не выводить, не восстанавливать их в клиенте из приватных полей.
- TeamCard: логотип/название, статистика и подтверждённый состав, если backend это предоставляет. Пустое фото → аккуратный графический fallback.

### 4.7 Новости, партнёры, правила, документы

- NewsCard + отдельная статья; публикация зависит от CMS, изображения имеют alt и правильные соотношения.
- Партнёры: только активные/опубликованные, реальные HTTPS ссылки, понятное разделение статуса.
- Длинный регламент: оглавление, поиск по тексту, доступные заголовки, корректная типографика и версия.
- Юридические документы: только утверждённые версии; не заменять отсутствующий текст фальшивыми шаблонами.
- Cookies/согласия: законные назначения, выключенный по умолчанию маркетинговый opt-in, доступная политика.

### 4.8 Кабинет и конфигуратор

- Общая шапка с публичным сайтом, но без тяжёлой публичной навигации внутри формы.
- Несколько автомобилей, версии конфигураций FRONT / SUB / REAR, питание, короб, описание, история, QR/регистрации.
- Каталог: **только существующие ID бренда/модели**; произвольную модель сохранять нельзя; запрос на новую модель — отдельный процесс.
- Обязательны только минимально необходимые сведения об оборудовании; доп. описания и параметры короба необязательны, если текущий backend не требует иного.
- Снимки оборудования прошедших этапов неизменяемы. При повторной регистрации вопрос «Менялось ли оборудование?».
- Функциональный источник истины — существующий backend, а не показанный в Figma текст.

## 5. Мобильная навигация и доступность

- Тестовые ширины `360, 390, 428, 768, 1024, 1440` + Safari iPhone.
- Хедер высотой примерно 56–64px (без учёта safe area); меню: закрывается Escape/переходом/кликом снаружи; фокус корректно возвращается.
- Нижняя навигация ЛК: одна опорная поверхность, `position: fixed` с `bottom: 0`, учёт `env(safe-area-inset-bottom)`, никакой второй полосы при скролле.
- Минимум интерактивного tap-target **44 × 44 CSS px**; видимый focus ring.
- При открытии клавиатуры поля видны, текст не увеличивает всю страницу, блокирующие CTA не заслоняют инпуты.
- При зуме 200% и увеличении системного шрифта интерфейс не обрезает обязательный контент.
- Разные состояния: loading, empty, error, pending, success, disabled, network failure, save conflict.
- Анимации мягкие (120–220ms); режим `prefers-reduced-motion` убирает смещения.

## 6. Безопасная архитектура внедрения в React

1. Финальная визуальная приёмка Figma + mobile экраны. **Не считать первые 6 готовыми, пока нет визуальной проверки.**
2. Выносить публичные компоненты из огромного `frontend/src/App.tsx` постепенно, с сохранением API контрактов; не переписывать приложение целиком.
3. Вводить стили в области `.public-site` / `.participant-portal`. **Админские `.main .content` и тёмный сайдбар не менять.**
4. Подключать CMS данные и существующие `/stages/public`, `/records/current`, `/site-settings/public`, `/results/stage/:id` без заглушек в production.
5. Разделять PR: shell/tokens → home → stages → results/records → content/legal → cabinet → configurator. Конфликты с открытыми PR проверять перед каждым merge.
6. Playwright: гостевой desktop/mobile путь, навигация/back-forward, прямые URL/refresh, фильтры, реальные пустые состояния, iPhone safe area и input focus. CI+browser acceptance обязателен.
7. Поддержка клавиатуры, WCAG contrast и минимизация CLS/layout jumps — критерии не менее важные, чем внешний вид.
