# USD — аудит защиты от взлома, 05.11.2026

Статус: текущий локальный проход завершён. Найдено6 подтверждённых проблем безопасности/валидации; дополнительные риски отделены от runtime-находок. Версия701d624476505b071edaf8a3985acd4e91b45c7a. Локальный API127.0.0.1:3302, отдельная БД usd_ui_audit. Используются3 одноразовых аккаунта A/B/C, закрытые профили/авто, конфигурации и чужая регистрация. Production не атакуется. Секреты и токены в доказательства не записываются.

## Подтверждённые проблемы

### SEC-01 · P1 · Поиск исторического профиля раскрывает закрытый профиль и госномер чужому аккаунту

Новый подтверждённый аккаунт C без participantId отправляет POST /auth/profile/historical-candidates с fullName:АудитСкрытый. Сервер отвечает201 и отдаёт имя/фамилию, город, марку/модель и registrationNumber скрытого участника, хотя Participant.isPublic=false и Car.isPublic=false. Проверены положительные контроли приватности: анонимные GET /participants/:id и /cars/:id возвращают404. В поиске canSelfLink=false; запрещённая привязка возвращает403, но данные уже раскрыты. Воспроизведено также через настоящее поле браузера.

Причина: backend/src/auth/auth.service.ts:664–699 выбирает все профили без user, без фильтра isPublic, и включает city/cars.registrationNumber. Проверка canSelfLink не защищает уже сериализованные данные.

Исправление: закрытые профили выдавать только после проверки принадлежности аккаунту по доверенному legacy email/другому подтверждению; посторонним возвращать минимальный нейтральный результат без города/машины/госномера. Не раскрывать номер только ради сравнения совпадений. Повторная проверка: чужой verified account не получает эти поля, владелец может безопасно восстановить свою историю.

Доказательства: cases.jsonl — hidden-public-profile, hidden-public-car, hidden-historical-candidate, hidden-disclosure-check; ui-hidden-profile-search.png. Все значения синтетические. Это утечка авторизованному новичку, не анонимный доступ ко всей базе.

### SEC-02 · P1 · Access JWT работает после logout

POST /auth/logout с соответствующим refreshToken →201; GET /auth/me с прежним accessToken →200. Повторный refresh после logout →401: refresh действительно отозван, но access остаётся рабочим. Ранее AUTH-02 подтверждён повторно.

Причина: JWT guard проверяет пользователя/роль, но не конкретный отозванный sessionId/authVersion. TTL по умолчанию15 минут. Смена пароля и reset проверены отдельно: старый access также возвращает200, тогда как refresh уже отозван и старый пароль отклоняется. Украденный access можно использовать до истечения срока. Исправление: привязать access к session/authVersion и проверять отзыв на сервере; тестировать logout, revoke-all, password/reset отдельно. Доказательство: cases.jsonl — logout-a/access-after-logout/refresh-after-logout.

### SEC-03 · P1 · Долгоживущий refreshToken раскрывается JavaScript

Ответ /auth/login содержит refreshToken в JSON. frontend/src/api.ts сохраняет usd_refresh_token в localStorage, несмотря на HttpOnly cookie. Это ранее AUTH-01. Проверка XSS ниже не дала исполнения: наличие отдельной XSS этим пунктом не утверждается. Однако при появлении XSS украсть этот токен можно из JS-контекста. Исправление: cookie-only refresh, убрать JSON-копию и старый storage, с сохранением CSRF-защиты.

### SEC-04 · P2 · Неожиданный тип participantId вызывает500 вместо валидации400

POST /auth/profile/link-historical от C: participantId:{"$ne":null} →500 Internal server error. Контроллер auth.controller.ts:281–288 использует TypeScript inline-type вместо валидируемого DTO; auth.service.ts:737 вызывает .trim() у значения, не проверив тип. Сервер не отдаёт stack trace в ответе и продолжает обслуживать запросы. Это дефект валидации/обработки ошибок, не доказательство SQL-инъекции или остановки сервера. Исправление: DTO с IsString/IsUUID и проверкой длины, fail400 до сервиса.

### SEC-05 · P1 для приватности релиза · Контактные данные в публичном архиве репозитория

Ранее подтверждён PRIV-18: backend/data/historical-xlsx.json в публичном GitHub содержит666 email-подобных значений,484 уникальных. Реальные адреса не выводились. Авторизация приложения не защищает опубликованный файл. Допустимость публикации каждого адреса неизвестна. Исправление: проверить основания публикации, перенести исходные контакты в закрытое хранилище, оставить обезличенные fixtures; очистку истории/зеркал согласовать отдельно, не потеряв оригиналы. Это прежняя находка, не результат SQL-атаки.

## Что выдержало текущие попытки

- 60 реальных HTTP-запросов в первом пакете; отдельные записи literal-storage и disclosure-check не считаются HTTP-запросами.
- Внедрение role:ADMIN/isAdmin/customRoleId/user.role/participantId в профиль и role в login →400. Административное назначение ADMIN/custom role, создание admin-аккаунта обычным участником и чтение admin API →403. Подмена X-Role/X-User-Role/X-User-Id не помогла.
- Подмена sub/role в JWT при старой подписи и alg:none →401.
- Чужие PATCH профиля/авто, чтение/создание чужих конфигураций, версии, регистрация, отмена и смена конфигурации регистрации →403; попытка переписать owner собственного авто →400. Собственные контрольные чтения →200. БД подтверждает: роли, customRoleId, participantId, владельцы/цвет авто и регистрация не изменились; запрещённый admin-аккаунт не создан.
- __proto__ и constructor.prototype получают200, но опасные ключи игнорируются: роль и данные не изменились, административный доступ не появился. Они не объявляются успешным prototype pollution из-за одного кода200.
- SQL-строки в Email/Password не обходят вход:400/401; JSON-объект вместо пароля →400. SQL-подобные city-строки хранятся буквально, сохранение занимает13–20 мс, запросы поиска10–17 мс. Проба pg_sleep(1) в пароле отклоняется за247 мс, сопоставимо с bcrypt-проверкой245 мс. Это ограниченные проверки, не доказательство отсутствия SQLi во всех маршрутах. Найденные raw SQL в просмотренных сервисах используют параметризованные Prisma tagged templates, RawUnsafe не найден.
- Через UI: email с SQL-строкой блокируется HTML validity.typeMismatch; с валидным email и SQL-паролем сервер показывает «Неверный email или пароль». API отдельно проверен в обход HTML-валидации.
- Безопасный сохранённый SVG/onload-маркер показан как текст в публичном профиле: eventElements=0, markerExecuted=null. Это проверка конкретного React-rendering, не всего XSS attack surface.

### SEC-06 · P1 · Reset-токен используется дважды в конкурентных запросах

На одноразовом аккаунте B создан настоящий PasswordResetToken, raw-token сохранён только в памяти теста. Два одновременных POST /auth/reset-password с одним токеном и разными паролями получили201/201. Проверка bcrypt по конечному passwordHash подтверждает: победил пароль второго запроса. Следующий последовательный запрос с тем же токеном получает400, usedAt уже заполнен. Это гонка, а не отсутствие проверки usedAt вообще.

Причина: backend/src/auth/auth.service.ts:1482–1513 читает/проверяет токен и считает hash до транзакции; :1515–1532 меняет пароль и ставит usedAt по одному id без условного usedAt:null, блокировки или атомарного захвата. Оба запроса успевают пройти проверку до записи.

Влияние: при одновременном использовании одной действительной ссылки второй запрос перезаписывает новый пароль первого. Для атаки нужен действительный reset-токен; обход получения самого токена не найден.

Исправление: в одной транзакции атомарно захватить действительный неиспользованный токен (условное обновление с usedAt:null/expiresAt>now и проверкой count=1 либо SELECT FOR UPDATE с повторной проверкой), после чего изменить пароль и отозвать сессии. При проигранной гонке возвращать400. Приёмка: из двух конкурентных запросов ровно один успешен, второй не может изменить passwordHash, повторный токен отклоняется.

Доказательства: reset-race.json; cases.jsonl — reset-race-first/reset-race-second/reset-token-reuse-after-race. Одноразовость токенов соответствует рекомендации [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html); конкретная неатомарность подтверждена локальным тестом.

### R-01 · Требует S3-проверки · Повторный PUT после complete

MediaService выдаёт presigned PUT на тот же objectKey, который затем публикует после проверки. Не найден переход staging→immutable-final key. Возможность перезаписи после complete зависит от реального object storage/policy и в этом проходе не воспроизведена. Перед релизом проверить PUT A→complete→PUT B по старой подписи в отдельном тестовом bucket. Ожидание: опубликованный объект не меняется. Не выдавать эту гипотезу за подтверждённый RCE/обход загрузки.

### R-02 · Проверка формата файлов ограничена

Проверки signature в media.service.ts не равны полному ограниченному декодированию изображения/OOXML: для DOCX проверяется ZIP magic. Предыдущая MEDIA-05 остаётся замечанием по валидации: нужны malformed ZIP/DOCX, безопасные лимиты распаковки и размеры изображений на тестовом S3. Загрузка исполняемого содержимого в production не проводилась.

### R-03 · В frontend nginx.conf нет CSP

API выставляет CSP, но это не добавляет политику HTML-приложению. Репозиторный frontend/nginx.conf CSP не задаёт. Неизвестно, добавляет ли её настоящий edge proxy; заголовки Vite-dev не использовались как доказательство production-уязвимости. Рекомендация: согласовать CSP для HTML/direct routes, начать с Report-Only и проверить приложение. XSS в протестированном профиле не найдена.

### R-04 · DevDependencies и запуск контейнера

Backend Dockerfile выполняет полный npm ci и сохраняет devDependencies в единственном runtime-stage. Среди advisory-пакетов tmp/undici есть high. Достижимость этих dev-пакетов из внешнего запроса не доказана; production-only scan даёт0. Dockerfile также не задаёт USER — без override процесс будет root; фактическая production identity не проверена. Рекомендация: multi-stage/runtime-only dependencies, обновить dev-цепочки, непривилегированный UID. Пример advisory сверён с [GitHub Advisory Database](https://github.com/advisories/GHSA-2m5v-pch6-74hx); список актуального сканирования сохранён в backend-all-dependencies.json.

## Приоритет перед релизом

1. SEC-06: атомарное погашение reset-токена и конкурентный regression-test.
2. SEC-01: убрать приватные поля из чужих результатов historical-candidates.
3. SEC-02: реальный отзыв access после logout/password/reset. [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html) отдельно описывает рассинхронизацию JWT после завершения сессии и серверный отзыв.
4. SEC-03: cookie-only refresh и удаление JS-копии; сохранить рабочую CSRF-защиту.
5. SEC-05: обработать публичный архив контактов; не уничтожать оригиналы и не переписывать историю без отдельного решения владельца.
6. SEC-04: DTO для inline body; ошибки типов должны давать400.
7. Закрыть R-01…04 на релизной инфраструктуре и повторить негативные тесты.

Рекомендация по SQL: сохранять разделение SQL-структуры и параметров; валидатор ввода не заменяет parameter binding. [OWASP SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).

87 реальных запросов API плюс браузерные проверки. SQLi, подмена ADMIN, подделка JWT, проверенные IDOR, XSS-маркер и CSRF-logout не удались. Это результат перечисленных сценариев, не заявление об отсутствии всех возможных атак. Подтверждено6 проблем:5 P1 и1 P2; из них SEC-01/04/06 выявлены текущим проходом, SEC-02/03/05 — перепроверены или перенесены из предыдущего аудита с указанными доказательствами.
