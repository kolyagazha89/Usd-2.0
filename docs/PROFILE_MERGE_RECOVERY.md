# USD: объединение дублирующихся участников — безопасность и восстановление

Статус: реализация ADMIN-only, применение к реальным профилям — **только отдельным явным действием ADMIN**. Выложенный код **не запускает массовое объединение**. Общий выпуск приложения и разрешение объединить конкретных людей — разные решения.

## Как выполняется операция

1. ADMIN выбирает **переносимый** и **основной** профили. До подтверждения открываются read-only сравнение и отдельная проверка конфликтов.
2. При двух аккаунтах, разных ФИО/датах, неоднозначных командах, хотя бы одном пересекающемся этапе (включая отменённые заявки), пересекающейся инспекции, дублирующемся госномере, незавершённых заявках на привязку, разных архивных email и прочих неоднозначностях **объединение запрещено**. Нет ни автоматического выбора, ни удаления второго аккаунта.
3. ADMIN вручную вводит первые восемь символов ID переносимого профиля. Сервис повторяет проверки под **сортированными advisory locks** для обеих идентичностей в **SERIALIZABLE** транзакции PostgreSQL 18.
4. Атомарно переносятся *ссылки на участника*, не исходные результаты и не объекты истории: автомобиль, регистрация, общая инспекция, рекорд, дисквалификация, архивная строка, аккаунт/членство (если отсутствует конфликт). ID всех этих записей, классы, номера, значения результатов, привязки к версии оборудования и зафиксированная командная принадлежность **остаются прежними**.
5. Исходная запись **Participant остаётся в БД** как скрытый alias. Сохраняются исторический ID, USD QR, фотомедиа, рассмотренные заявки и аудит. Строка `ParticipantMergeRedirect` фиксирует старый ID → основной ID, ADMIN, время и recovery manifest. Старые публичные URL и USD QR разрешаются через основной профиль.
6. Операция идемпотентна только при повторной отправке **той же пары ID**; другой адрес назначения блокируется. При ошибке в середине транзакции PostgreSQL откатывает все изменения, включая alias и аудит.

## Что сохранять для восстановления

В `ParticipantMergeRedirect.recovery` записываются `version=1`, `sourceWasPublic`, `targetOriginal` (заполненные первоначально поля основного профиля), `copiedLegacyEmail`, `moved` с точными ID автомобилей, регистраций, инспекций, рекордов, дисквалификаций, строк импорта, исходного аккаунта и членства, а также ID завершённых медиазагрузок, **оставленных без изменений**. Это не автоматическая команда восстановления и не повод удалять архивные строки. Доступ к манифесту должен оставаться только у уполномоченного администратора БД; личные данные нельзя выводить в issue, CI или публичные журналы.

## Аварийная процедура (выполняется только ответственным оператором)

1. Остановить операции с конкретными профилями; зафиксировать точный SHA приложения, ID пары, время и оператора. Не останавливать всю БД и не выполнять reset/migrate resolve.
2. Проверить свежую локальную резервную копию PostgreSQL и RustFS на согласованном втором диске. **Сначала восстановить изолированную копию**. До любой операции на живой БД сопоставить манифест с реальными существующими записями.
3. Сверить **каждый ID** из `moved`: он должен всё ещё принадлежать целевому профилю и соответствовать неизменному исходному регламенту/номеру/результату. Любая регистрация, пересмотр, новый результат, заявка, команда или новая версия оборудования после объединения — повод **остановить автоматический откат** и разобрать конфликт вручную.
4. На изолированной копии в одной SERIALIZABLE-транзакции вернуться к исходной принадлежности **только перечисленных** ID; вернуть ранее пустые поля основного профиля из `targetOriginal` лишь если после операции они не изменились. Сохранить неизменными UUID результатов, номера и версии конфигураций.
5. Исторические emails: удалить целевую копию лишь если манифест отмечает `copiedLegacyEmail=true`, она точно совпадает с созданной копией и позже не менялась. Архивный email источника не трогать. Медиа RustFS **не удалять**, потому что на него могут ссылаться обе истории.
6. Восстановить прежнюю видимость источника, убрать redirect только после полной проверки зависимостей, записать **новую** запись аудита о восстановлении; оригинальный аудит объединения не стирать. Проверить старые URL/QR, статусы доступа, номера, классы, результаты, команды и отсутствие дубликатов.
7. Только после успешной изолированной репетиции, независимого одобрения и нового backup повторить согласованный план в рабочей системе. Если риск недоказуем — оставить alias и вынести спор на ручное решение.

### Проверки

`backend/test/profile-link-concurrency.e2e-spec.ts` (изолированная PostgreSQL 18, `USD_PROFILE_LINK_RACE_TEST=1`) проверяет перенос реальных связей и сохранность ID, оба старых вида ссылок, повторный запрос и **откат транзакции при искусственной ошибке БД после уже выполненных UPDATE**. Реальный откат **после завершённого объединения** не реализован как автоматическая кнопка; репетиция всей процедуры восстановления на копии и операционная приёмка остаются обязательными до использования в спорном случае.
