# USD на домашнем Windows-ПК

Подготовленная конфигурация для одного ПК i5 / 16 ГБ, SSD, Windows с WSL2 и Docker Desktop. Это не подтверждение публикации или нагрузочной ёмкости.

## Схема

Интернет → Cloudflare Tunnel → gateway → frontend и /api → NestJS → PostgreSQL. Один HTTPS-origin, refresh credential только в HttpOnly cookie. База и API не открывают порты наружу; локальный просмотр gateway — 127.0.0.1:8088. Для входа и камер используется настоящий HTTPS-домен.

Закрепление LAN-адреса в роутере не создаёт внешний статический IP. Туннель использует исходящие соединения. Настройка named tunnel: hostname APP_DOMAIN, service http://gateway:80. Не открывать роутерные порты этой конфигурации. Действующий корневой домен не переключать до приёмки новой версии.

## Порядок подготовки

1. Поддерживаемая Windows, WSL2, Docker Desktop с Linux-контейнерами. Около 6 ГБ для контейнеров; проверить свободный SSD. Ограничения памяти не заменяют нагрузочный тест.
2. Автозапуск Docker Desktop, тест после реальной перезагрузки. Restart policy не запускает сам Desktop. Владелец задаёт режим сна, окно обновлений и резервное питание.
3. Скопировать .env.example в .env, заполнить собственные секреты, существующие S3 и email. Заглушек оставаться не должно. Секреты не отправлять в GitHub или чат.
4. До первого API-старта создать и восстановить копию текущей БД в тестовую среду. Проверить данные и условия исторического bootstrap: backend автоматически применяет миграции. Пустой volume не заменяет перенос данных.
5. Проверить docker compose config --quiet, собрать docker compose build. Сначала запустить только db и восстановить согласованную копию данных.
6. Production-старт API и изменение DNS — после отдельного подтверждения владельцем. Затем docker compose --profile public up -d и проверка HTTPS, маршрутов, входа, cookie, QR на iPhone/Android, почты, фото и результатов.

## Резервирование

backup ежедневно создаёт custom pg_dump, проверяет читаемость архива и хранит 14 дней в volume backups. Проверка архива не заменяет восстановление. Копировать архивы на независимый носитель/хранилище: volume на том же диске не защищает от поломки диска. S3 резервируется отдельно. Не применять docker compose down -v при обычном обновлении: это удаляет данные.

## Площадка

Домашний ПК остаётся главным; отдельный ноутбук получает только пакет выбранного этапа и обслуживает судей через локальный Wi-Fi. VPN не восстанавливает отсутствующий мобильный канал. Полная offline-синхронизация этим compose не реализована: см. docs/OFFLINE_MODE.md. Не копировать всю production-БД с аккаунтами на судейские устройства.

Один домашний ПК и канал остаются единой точкой отказа публичного сайта. Несколько API-реплик потребуют общего limiter. Текущая конфигурация рассчитана на одну реплику. Доступ к новой версии открывается после восстановления, тестов и сверки опубликованного коммита.
