# DNS для app.usd-russia.ru и api.usd-russia.ru через REG.RU + Cloudflare Tunnel

> **Не выполнять DNS-переключение сейчас.** Эта инструкция подготовлена заранее. До переключения должны пройти локальные проверки приложения, а публичная конфигурация frontend/API должна быть отдельно подготовлена и проверена. Не меняйте существующие записи корневого домена `usd-russia.ru`, почты и других сервисов.

## Что хотим получить

- `https://app.usd-russia.ru` — публичный сайт ЮСД.
- `https://api.usd-russia.ru` — API.
- `usd-russia.ru` и `www.usd-russia.ru` — оставить без изменений.
- Входящие порты на роутере не открывать. Cloudflare Tunnel сам устанавливает исходящее соединение с Cloudflare.

## Сначала определите, где обслуживается DNS

Регистратор домена и DNS-хостинг — не обязательно одно и то же.

1. Войдите в личный кабинет REG.RU и откройте домен `usd-russia.ru`.
2. Найдите раздел DNS-серверов / NS и запишите текущие NS-записи. Ничего пока не меняйте.
3. Откройте раздел управления DNS-зоной и посмотрите, где находятся действующие записи для корня домена, `www`, почты (MX), SPF, DKIM и DMARC.
4. В Cloudflare откройте аккаунт и проверьте, добавлена ли зона `usd-russia.ru` и какой у неё статус.

### Вариант A — DNS-зона остаётся в REG.RU

Используйте этот вариант только если Cloudflare позволяет подключить пользовательские hostnames к Tunnel при внешнем DNS (частичная настройка / CNAME setup).

После создания отдельного Cloudflare Tunnel и добавления в нём публичных hostname получите **Tunnel UUID**. В REG.RU откройте DNS-зону и добавьте две записи:

| Тип | Имя / хост | Значение / целевой хост | TTL |
|---|---|---|---|
| CNAME | `app` | `<TUNNEL-UUID>.cfargotunnel.com.` | По умолчанию |
| CNAME | `api` | `<TUNNEL-UUID>.cfargotunnel.com.` | По умолчанию |

Замените `<TUNNEL-UUID>` на реальный UUID туннеля из Cloudflare. Не вводите угловые скобки. Если интерфейс REG.RU сам добавляет точку в конце доменного имени, это нормально.

- Если для `app` или `api` уже существуют A/AAAA/CNAME-записи, сначала выясните, используются ли они. У одного имени не должно быть конфликтующих CNAME и A/AAAA.
- Не создавайте wildcard-запись `*`.
- Не меняйте NS и не удаляйте записи корня, `www`, MX, TXT, SPF, DKIM или DMARC.
- После сохранения проверьте, что Cloudflare Tunnel настроен принимать именно `app.usd-russia.ru` и `api.usd-russia.ru` и направлять их соответственно на `http://frontend:80` и `http://api:3000` внутри Docker-сети.

Если Cloudflare не позволяет привязать эти hostname при DNS у REG.RU, не пытайтесь подбирать случайные IP-адреса. Используйте вариант B либо уточните поддержку partial/CNAME setup в Cloudflare.

### Вариант B — DNS-зона переносится на Cloudflare

Это более крупное изменение. Оно может затронуть почту и другие сервисы, поэтому выполнять его следует только после инвентаризации зоны и отдельного согласования.

1. Добавьте `usd-russia.ru` в Cloudflare и просмотрите импортированные DNS-записи.
2. Сверьте каждую существующую запись с текущей зоной REG.RU: корень, `www`, MX, все необходимые TXT (SPF/DKIM/DMARC и подтверждения сервисов), а также остальные поддомены.
3. Убедитесь, что критичные записи восстановлены в Cloudflare **до** смены NS.
4. В REG.RU замените NS на пару nameserver-адресов, которую Cloudflare покажет именно для вашей зоны. Не копируйте nameserver-адреса из чужих инструкций.
5. Дождитесь, пока Cloudflare подтвердит активный статус зоны. Проверьте сайт и почту.
6. В DNS Cloudflare создайте CNAME для `app` и `api`, направив обе записи на `<TUNNEL-UUID>.cfargotunnel.com`. Для Tunnel включите проксирование Cloudflare, если его требует мастер настройки.

Не выбирайте вариант B, если не готовы проверить почту и все существующие поддомены после делегирования.

## Настройка самого Tunnel

В Cloudflare Zero Trust / Networks / Tunnels (названия разделов могут отличаться):

1. Создайте отдельный туннель, например `usd-laptop`, и сохраните token только в локальном `deploy/laptop/.env` как `CLOUDFLARE_TUNNEL_TOKEN`. Не отправляйте его в чат, коммиты или тикеты.
2. Добавьте публичные hostname:
   - `app.usd-russia.ru` → сервис `http://frontend:80`
   - `api.usd-russia.ru` → сервис `http://api:3000`
3. Убедитесь, что оба маршрута относятся к этому Tunnel и что HTTPS обслуживается Cloudflare.
4. В Compose профиль Tunnel включается отдельно; по умолчанию он отключён. Не включайте его до локальной приёмки.

## Обязательная проверка перед публичным включением

Текущий laptop frontend image намеренно собран с API URL `http://localhost:3000`, а API и MinIO CORS пока настроены только на localhost. **С этим локальным образом нельзя безопасно публиковать сайт через Tunnel.** Перед DNS-переключением необходимо подготовить и протестировать публичную конфигурацию frontend/API, включая:

- браузерный адрес API `https://api.usd-russia.ru` (или проверенную схему reverse proxy);
- CORS и CSRF allowlist для `https://app.usd-russia.ru`;
- secure cookies, корректный proxy trust и HTTPS;
- публичные media/upload URL и CORS для `https://app.usd-russia.ru`;
- health-check, логин, регистрацию, загрузку и просмотр файлов;
- резервную копию и проверенный план восстановления;
- отдельное подтверждение владельца на DNS cutover.

До завершения этих проверок оставьте `cloudflared` выключенным, DNS без изменений, а Railway/Cloudflare Worker и production DB — как есть.

## Проверка DNS после согласованного переключения

В Windows PowerShell:

```powershell
Resolve-DnsName app.usd-russia.ru
Resolve-DnsName api.usd-russia.ru
```

Затем проверьте HTTPS:

```powershell
curl.exe -I https://app.usd-russia.ru
curl.exe -I https://api.usd-russia.ru/
```

Ответ API может быть JSON или редиректом/ответом приложения в зависимости от конфигурации; важны валидный TLS-сертификат и ожидающийся ответ сервиса. Не считайте один лишь успешный DNS lookup подтверждением исправности сайта.

## Откат

Если после согласованного переключения возникла проблема, верните только изменённые записи `app` и `api` к сохранённым прежним значениям. Если менялись NS, откат NS может занять время из-за DNS-кэша; не удаляйте старую зону, пока не убедитесь, что сервисы восстановились. Корневой домен и почтовые записи не меняйте без отдельной необходимости.
