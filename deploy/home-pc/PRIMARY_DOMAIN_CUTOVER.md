# USD — подготовка переключения с app.usd-russia.ru на usd-russia.ru

**Состояние:** только готовность к будущему переключению. **DNS REG.RU, CloudPub, Tilda, Ubuntu и рабочая база не меняются этим PR.**
Владелец отдельно подтвердит окно реального переключения после приёмки онлайн-релиза. До этого основным остаётся `https://app.usd-russia.ru`.

## Устройство после переключения

- `https://usd-russia.ru` — публичный сайт, регистрация и кабинеты.
- `https://api.usd-russia.ru` — существующий API; PostgreSQL 18 и RustFS остаются прежними.
- `https://app.usd-russia.ru` — перенаправление 301 на соответствующие пути основного сайта **только после готовности сертификата и функциональной проверки**. До этого работает как сейчас.
- `https://www.usd-russia.ru` — 301 на apex после настройки отдельного TLS/публикации.
- `APP_DOMAIN=app.usd-russia.ru` остаётся **внутренним идентификатором проверяемого развёртывания**, менять его на apex нельзя: действующие release, backup и restore gates на него опираются.

## Что подготовлено в коде

1. Флаг активации на Ubuntu — два необязательных `.env` значения, по умолчанию выключены:
   ```dotenv
   USD_PUBLIC_FRONTEND_ORIGIN=https://app.usd-russia.ru
   USD_FRONTEND_ALLOWED_ORIGINS=https://app.usd-russia.ru
   ```
   После отдельного одобренного переключения **только оба сразу**:
   ```dotenv
   USD_PUBLIC_FRONTEND_ORIGIN=https://usd-russia.ru
   USD_FRONTEND_ALLOWED_ORIGINS=https://app.usd-russia.ru,https://usd-russia.ru
   ```
   Эти значения запитывают FRONTEND_URL, CORS_ORIGINS и CSRF_TRUSTED_ORIGINS в Compose. Release helper принимает только перечисленные защищённые origins; произвольный hostname, HTTP, userinfo, `www` как API-Origin и укороченный CORS-list отклоняются. `API_DOMAIN` остаётся `api.usd-russia.ru`.

2. Build-time SEO: `VITE_PUBLIC_SITE_ORIGIN` по умолчанию app, может стать только `https://usd-russia.ru`. Готовые `*.html`, canonical, OG URL/image, structured data и robots sitemap используют один выбранный origin. Динамическая metadata в браузере уже привязана к `location.origin`, а API sitemap берёт `FRONTEND_URL`.

3. Публикация GHCR принимает репозиторную переменную `USD_PUBLIC_SITE_ORIGIN=https://usd-russia.ru` **только при** `USD_PRIMARY_DOMAIN_CUTOVER_APPROVED=true`. Пока обе переменные не выставлены владельцем, образ с canonical для app неизменен. Репозиторные переменные — не разрешение на изменение DNS и не отмена серверных проверок.

4. Read-only release verifier допускает только единственный межсайтовый редирект `app.usd-russia.ru → usd-russia.ru`, блокируя переходы API и сторонние hostnames. Проверка точного SHA API и frontend, маршрутов, изображений и приватных API сохраняется.

## Этап 0: основной домен уже подключён, но API недоступен в браузере

На первом этапе подключения REG.RU/CloudPub новый `usd-russia.ru` может
отдавать frontend раньше, чем оператор переключит `FRONTEND_URL` и
канонический SEO origin. Это нормальный промежуточный режим.

В релизе API допускает **только точный** `https://usd-russia.ru` как
дополнительный browser origin, если рабочий production CORS/CSRF уже
допускает `https://app.usd-russia.ru`. Решение применяется в серверном
CORS и CSRF, а также в privacy-first счётчике публичных страниц.
Не используются `*`, произвольные домены, HTTP и маски поддоменов.
На существующих Ubuntu `.env` и Docker Compose менять ничего не требуется:
достаточно штатного CI-gated обновления обоих образов и проверенного SHA.
`app.usd-russia.ru` остаётся рабочим. Переход `FRONTEND_URL`, писем,
canonical, 301 и PUSH остаётся отдельной операцией с rollback.

Важно: открывающийся frontend не гарантирует работоспособность API.
После выпуска исправления проверять отдельно:
- `https://api.usd-russia.ru/release` и `https://usd-russia.ru/usd-release.json` показывают один релиз;
- в DevTools Network запросы с `Origin: https://usd-russia.ru`
  к `api.usd-russia.ru` возвращают конкретный
  `Access-Control-Allow-Origin: https://usd-russia.ru`, не `*`;
- опубликованные этапы и результаты грузятся, а вход/регистрация/согласия
  проходят полный браузерный сценарий;
- приложение на старом `app` не регрессирует;
- если новый домен или API не отвечает по сети (timeout/DNS/SSL),
  CORS-исправление само по себе это не лечит — смотреть CloudPub, DNS и HTTPS.

## До переключения — обязательные условия

- [ ] Убедиться, что рабочая Ubuntu действительно использует текущий `main`: оба `/release` равны успешному SHA. Исправление доступа судьи должно быть на сервере и проверено.
- [ ] Сохранить и проверить **независимые** резервные копии PostgreSQL и RustFS; убедиться, что есть способ восстановить старые образы и `.env` без очистки томов.
- [ ] Отдельно проверить регистрационный сценарий обычного участника и судьи, юридические согласия, подтверждение email, документы, этапы, фото, результаты, админку на app.
- [ ] Проверить, где хранятся DNS-записи REG.RU: авторитетные NS, A/AAAA/CNAME root и www, TXT, MX, SPF, DKIM, DMARC, подтверждения Яндекс/Google; сохранить снимок всей DNS-зоны. **Если NS у Tilda, нельзя считать, что A запись контролируется REG.RU.**
- [ ] В CloudPub создать **отдельный** mapping apex на существующий frontend tunnel; получить выданные CloudPub конкретные адреса/записи и убедиться в HTTPS. Не придумывать IP CloudPub.
- [ ] Проверить редирект www, серверный TLS, доступность `api.usd-russia.ru` и отсутствие раскрытия PostgreSQL/RustFS.
- [ ] Проверить, что на основном домене нет неизвестного назначения/внешней почтовой зависимости; менять только необходимые A/AAAA/CNAME/TXT сайта.

## Будущая последовательность (не выполнять при подготовке кода)

1. Согласовать окно, backup/rollback и зафиксировать текущий live SHA. Не запускать установщик с изменённым APP_DOMAIN; НЕ запускать `docker compose down -v`.
2. Проверить первичный CloudPub маршрут и сертификаты. Переходить к DNS REG.RU только после готовности origin. Сначала обеспечить reachable apex, затем включать канонический SEO и отправку ссылок из API.
3. Под наблюдением на Ubuntu **одновременно** сменить два `USD_...` значения и пересоздать только API (если это согласовано); старый base frontend и его media/database не удалять. Важно: обычный root-owned release helper намеренно выявляет изменение `.env` относительно ещё работающего API как drift и **не может быть способом перехода из одного режима в другой**. Для самой первой смены требуется отдельная контролируемая процедура с сохранённой конфигурацией, отключённым timer и готовым rollback. Самостоятельно `.env` менять нельзя.
4. После подтверждённой доступности apex и API установить repo vars `USD_PUBLIC_SITE_ORIGIN` + `USD_PRIMARY_DOMAIN_CUTOVER_APPROVED`, получить **новый** SHA-кандидат с primary canonical, дождаться CI/signed GHCR и обновления Ubuntu через штатный release gate.
5. Проверить в анонимном браузере и на реальных телефонах: регистрация, кабинет, согласия, восстановление доступа, ссылки email, API CORS/CSRF, изображения, исторические протоколы, sitemap и robots. Отдельно убедиться, что `app` и `www` дают 301 с сохранением пути/параметров, а не 404.
6. Обновить Яндекс Вебмастер и Google Search Console, проверить старые индексированные пути Tilda и адреса регламентов. Не менять идентификаторы мероприятий или записи БД.
7. Перепроверить следующий unattended автодеплой, свежую резервную копию и независимые revision SHA.

## Важные ограничения

- Авторизационные cookie привязаны к браузерному/сетевому origin: после смены сайта пользователь может повторно войти. Сохранение старых API cookie зависит от их SameSite/Secure настроек.
- **Web Push не переносится между origins.** Подписчикам может понадобиться повторно включить PUSH на `usd-russia.ru`.
- 301 со старого app лучше включать после успешной приёмки нового origin; заранее постоянный редирект трудно отменить из-за кэша браузеров.
- Если после переключения что-либо работает неверно, откатить прежде всего CloudPub route и DNS на сохранённые записи; вернуть предыдущее origin в `.env` и предыдущую подписанную сборку по одобренной процедуре. DNS-кэши не обновятся мгновенно.
- Юридические документы, согласия и основание публичной публикации архивных ФИО требуют самостоятельной содержательной проверки; сам перенос домена не делает юридический блок завершённым.
